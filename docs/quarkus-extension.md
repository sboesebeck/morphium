# Quarkus Extension: CDI Integration for Morphium

!!! success "Jakarta Data TCK: 73 of 73"
    The repositories of this module run on `morphium-jakarta-data`, which passes all 73 tests of the standalone Jakarta Data 1.0 TCK suite (from the release after 6.3.14) — see [Conformance](jakarta-data.md#conformance-jakarta-data-tck).

`quarkus-morphium` is an **optional Morphium module** that integrates Morphium into
[Quarkus](https://quarkus.io) applications via a CDI producer, type-safe
`@ConfigMapping` configuration, declarative transactions, health checks, Dev Services,
Dev UI integration, and GraalVM native-image support. It also pulls in
[`morphium-jakarta-data`](jakarta-data.md) and generates Jakarta Data `@Repository`
implementations at **build time** via Gizmo bytecode generation — no runtime
reflection, no dynamic proxies.

!!! note "Optional module — the Morphium core does not depend on it"
    `de.caluga:morphium` has zero compile- or runtime dependency on this extension, on
    Quarkus, or on `jakarta.data-api`. Building the Morphium reactor without this module
    (`-DskipExtensions`) produces an unchanged core. You only need `quarkus-morphium` if
    you are building a Quarkus application against MongoDB via Morphium.

## What it provides

- **CDI producer** — `@Inject Morphium morphium;` anywhere in a Quarkus bean, backed by
  a single, application-scoped `Morphium` instance configured from
  `application.properties`.
- **Type-safe configuration** — every setting lives under `quarkus.morphium.*` as a
  `@ConfigMapping`, validated at build time instead of failing at runtime on a typo.
- **Declarative transactions** — `@MorphiumTransactional` on a CDI bean method wraps
  the method body in `startTransaction()`/`commitTransaction()`/`abortTransaction()`
  automatically, with `MorphiumTransactionEvent` CDI events (`BEFORE_COMMIT`,
  `AFTER_COMMIT`, `AFTER_ROLLBACK`) for cross-cutting reactions (audit logging,
  outbox publishing, etc.). Gracefully degrades to non-transactional execution on
  Azure CosmosDB, which is auto-detected.
- **Jakarta Data repositories** — declare a `@Repository` interface extending
  `CrudRepository`/`MorphiumRepository` from `morphium-jakarta-data`; the extension's
  build-time processor generates the implementation via Gizmo, with no reflection at
  runtime. See [Jakarta Data](jakarta-data.md) for the full query-derivation, JDQL, and
  pagination feature set — everything documented there works identically once
  generated by this extension.
- **Health checks** — MicroProfile liveness (`/q/health/live`), readiness
  (`/q/health/ready`, with connection-pool metadata), and startup (`/q/health/started`)
  probes registered automatically via SmallRye Health.
- **Micrometer metrics** — connection pool, cache and write-buffer gauges and counters
  (`morphium.driver.*`, `morphium.cache.*`, `morphium.write_buffer.*`) and a timer for the
  update operations (`morphium.operations.duration`). Active when Micrometer is on the
  application's classpath; see [Metrics](#metrics).
- **Dev Services** — a MongoDB container (optionally as a single-node replica set, so
  transactions and change streams work out of the box) starts automatically in dev and
  test mode when no explicit `quarkus.morphium.hosts` is configured — no Docker Compose,
  no manual setup.
- **Dev UI card** — live MongoDB connection info (hosts, database, replica-set mode,
  container ID) at `/q/dev-ui/`.
- **GraalVM native-image support** — every `@Entity`/`@Embedded` class (and Morphium's
  own reflection-dependent internals) is registered for reflection at build time; no
  manual `reflect-config.json`.
- **`MorphiumId` JSON serialization** — entities with `@Id MorphiumId id` serialize to
  a plain 24-character hex string over REST (both Jackson and JSON-B), and parse back
  from one — no serializer to write by hand.
- **Migration runner** — a lightweight, MongoDB-backed schema/data migration mechanism
  (`quarkus.morphium.migration.*`) with a distributed lock, so multiple application
  instances don't race to apply the same migration.

## Installation

```xml
<dependency>
  <groupId>de.caluga</groupId>
  <artifactId>quarkus-morphium</artifactId>
  <version>6.3.9</version>
</dependency>
```

This module follows Morphium's regular release versioning and is released in lockstep
with Morphium core; there is no separate version line to track. Building the reactor
(`mvn -pl quarkus-morphium -am verify`) builds this extension against the exact Morphium
core version in the same build.

## Metrics

With Micrometer on the classpath (for example `quarkus-micrometer-registry-prometheus`) the extension
registers these meters, all tagged with `database`:

| Meter | Type | Meaning |
|---|---|---|
| `morphium.driver.connections.pool`, `.in_use` | gauge | connections in the pool / borrowed |
| `morphium.driver.connections.borrowed`, `.released` | counter | cumulative |
| `morphium.driver.threads.waiting` | gauge | threads waiting for a connection |
| `morphium.driver.errors`, `.failovers` | counter | cumulative |
| `morphium.cache.hit_ratio`, `.entries`, `morphium.write_buffer.entries` | gauge | cache and write buffer |
| `morphium.operations.duration` | timer | update operations; tags `operation=update`, `update_type` (`set`, `inc`, `push`, ...) and `entity` |

The timer covers every update that fires the storage-listener events: the writer path (`Query.set`, `inc`, `push`, `pull`, ..., the bulk
context), the update builder (`Query.modify()`) and `findOneAndUpdate(Map)`, `updateOne` and `updateMany`. The `update_type` is the operator of the call
(`set`, `inc`, `push`, ...), `custom` for an update with several operators. A write that fails is not timed, because no event follows it. A write that a
buffered writer flushes on another thread is not timed either.

## Quick Example

```java
@Entity(collectionName = "products")
public class Product {
    @Id private MorphiumId id;
    private String name;
    private double price;
    private String category;
    @Version private long version;
    // getters/setters omitted
}

@Repository
public interface ProductRepository extends MorphiumRepository<Product, MorphiumId> {
    List<Product> findByCategory(String category);

    @OrderBy("price")
    List<Product> findByPriceGreaterThan(double minPrice);
}

@ApplicationScoped
public class ProductService {
    @Inject ProductRepository products;

    @MorphiumTransactional
    public Product create(String name, double price, String category) {
        var p = new Product();
        p.setName(name);
        p.setPrice(price);
        p.setCategory(category);
        return products.insert(p);
    }
}
```

```properties
quarkus.morphium.database=my-app-db
# Dev Services starts MongoDB automatically — no further config needed in dev/test.
```

## Testing without Docker

```properties
%test.quarkus.morphium.driver-name=InMemDriver
%test.quarkus.morphium.database=test-db
```

`InMemDriver` is Morphium's in-memory MongoDB emulation — `@QuarkusTest` classes run
against it with no container and no external MongoDB, exactly like the core Morphium
test suite.

## Testing against a real MongoDB

The module `quarkus-morphium-testing` (test scope) has the helpers for application tests:

```java
@QuarkusTest
@TestProfile(MongoMorphiumTestProfile.class)      // a real MongoDB, see below
@ExtendWith(ResetMorphiumExtension.class)          // an empty database before each test
class OrderServiceTest {
    @Inject Morphium morphium;

    @Test
    void cancelsAnOrder() {
        MorphiumTestSupport.load(morphium, order("o1"), order("o2"));   // fixtures, stored like the application stores
        ...
    }
}
```

- `MongoMorphiumTestProfile` runs the test with the pooled driver against a MongoDB container that Dev Services starts. With
  `MORPHIUM_TEST_HOSTS=host:27017` (environment variable or system property) it uses that server instead. The tests use their
  own database (`morphium-test`, override `database()` in a subclass); a subclass can also ask for a replica set (`replicaSet()`),
  which transactions need. `InMemMorphiumTestProfile` stays the choice for tests without a server.
- `MorphiumTestSupport.reset(morphium)` removes the documents of all collections of the database and clears the cache. It deletes
  instead of dropping, so the collections keep their indexes. `ResetMorphiumExtension` calls it before each test.
- `MorphiumTestSupport.load(morphium, entities...)` stores the entities with `Morphium.store`.
